# 知乎回答写作

写出用户自己的分析，不替用户编经历或决定立场。事实、必要条件和证据范围优先于文风；用户只要求改一段时，不扩写全文。

## 两阶段流程

写新回答分两轮进行；用户只要求改一段时，跳过头脑风暴，直接改。

1. **头脑风暴**：只出提纲，不写成段正文。列出：
   - 候选结论（一两句话，可给两三个方向供选）
   - 支撑论点，每条注明需要的事实或数据，已核实的给来源，未核实的标【待核实】
   - 值得回应的反方观点
   - 需要用户补的个人经历或立场，用【待补：……】标出
   - 段落顺序草案
   交出提纲后停下，等用户讨论、调整并确认，不在同一轮继续成文。
2. **正式写作**：按确认后的提纲成文，不擅自加入提纲外的论点；写作中发现提纲有问题时，先说明再改。

## 动笔与查证

- 保留用户给出的开头、论点和推理。有现成的用户回答样本时，读一两篇找语感，不假设固定的样本目录。
- 缺少影响论点的个人经历时，用【待补：……】标出并询问；不为了增加故事感强行加入经历。
- 研究和数据只有助于回答题目时才引用，不凑数量。查原始来源，核实作者、年份、具体发现和相关样本规模；期刊论文还需核对刊物，不直接采用媒体转述的数字。
- 说明研究对当前论点能支持什么、限制在哪里，不把群体结果直接套到个人，也不用“还是取决于人”代替分析。未查到依据的断言不作为事实写入；无法查证时标【待核实】。
- 默认正文用 [1] 标记，文末附来源及原始链接。影响结论的限制留在正文，旁支细节可放脚注。

## 用户的声音

- 开头第一段直接给结论，一两句话说清立场或答案，再展开主体论证；不寒暄、不写“谢邀”，不先铺背景。语体是书面化的口语，带分析腔。
- 段落较短，但句子表达完整判断，不靠碎片短句制造节奏。概念复杂时可编号，核心论断值得强调时再加粗。
- 表态可用“个人认为”“在我看来”；转折可用“但问题在于”“更准确地说”。按逻辑选词，不把这些短语当模板。
- 遇到实质反驳时正面回应；不确定处说清边界，不句句对冲。数据直接进入论证，交代必要的规模和背景。
- 以中文为主，idea、review 等有自然中文说法的词译成中文；API、Linux 等技术名称保留。中文用“ ”引号，中英文之间加空格。
- 幽默或反讽只在合适时一句带过，不强行加入。结尾可以停在具体事实或尚未解决的问题上，少用金句和连串反问，不例行总结。

## 改稿偏好

- 少用“你”指读者，说理时按语境用“我”或“我们”。避免“说实话”“挺怪的”等填充语，不用 emoji。
- 不靠“首先、其次”组织套话，少重复“所以”；连接词必须有实际逻辑作用。
- 避免抽象的“落在”、用“分成”代替“拆成”、用“算”代替“算账”的比喻，拿不准时选朴素说法。
- 删去“先说 X，因为 X 最具体”式写作过程解释，直接讲 X；“X 这边”式转场改为“对于 X”。
- 修辞举例通常一两项足够；必要的条件、步骤和对照项完整保留。

## 交付

完整回答默认约 900–1700 字，按题目和用户要求调整。头脑风暴轮只交提纲；正式写作轮直接交草稿及确有需要的【待补】或【待核实】项；局部改写只交所改部分。草稿供用户审阅，不替用户发布。

## 存档

用户发布后，按截图、回答链接或用户给出的**实际发布的文字**逐字存档，不按草稿存。存到 JD 仓库（`~/JD`）：

1. 文件：`11 Social/11.02 Zhihu/<YYYY-MM-DD> <问题标题>.md`。格式：
   ```markdown
   # <YYYY-MM-DD> <问题标题>

   - Question: [问题标题](问题链接)
   - Answer: [回答链接](回答链接)
   - Posted: <YYYY-MM-DD>

   ## Answer

   <逐字正文，含文末来源>
   ```
2. 在 `11 Social/11.02 Zhihu/README.md` 里加一行：链接 + 一句话说明。
3. 当天日记（`00 Periodic/<YYYY>/<MM>/W*/<YYYY-MM-DD>-<Ddd>.md`）里有对应任务就勾掉，并用 `[[文件名]]` 链到存档。
4. 按 JD 的 `Agents.md` 用 git 提交。
